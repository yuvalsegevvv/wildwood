# Dungeons (code map)

Area guide. Moved word for word from `CLAUDE.md` section 4 (the row written with the dungeons design); the design itself is `docs/DUNGEONS.md`.

## Where to change what

### Dungeons, the pure setup (the server's runs that use it are the next entry): the map tiles (24 x 24 cells of 2 m = 48 m; `DG_SET_BARE`, `dgRect`, `dgVariants`; the round hall is a boss arena's circle, `DG_BOSS_R` = 20 m = every `ARENAS` r), the seeded layout generator (`dgLayout`, `DG_MISSIONS`: the roles each mission needs, one boss hall each: every mission ends with a boss, no extraction), the baked grid both sides share (`dgBake`, with `boss` = the hall's circle as an arena `{x,z,r}`; `dgSolid` / `dgFree` / `dgSlide`, `dgLos`, the monsters' flow field `dgFlow` / `dgStep`), the three dungeons as data (`DG_THEMES`: land, `at` zone, walkers and guardians, boss, music, palette; `DG_LV` 30), their three new bosses (`DG_BOSSES`: model, pal, moves named by primitive, the `needs` still to build), the hourly offer of two mission types (`dgOffer`, `dgOfferLeft`: random but fair, UTC) and who may enter (`dgUnlocked`, `dgLevel`, `DG_LANDS`: the difficulty is the land's own zone tier setting; Wildwood's is locked at +0 and level 30 at +1, the Vale's and the Reach's level 30 at +0 after Hanami / Rimehold, +10 levels a tier above the base, entry from level - 5), party-size scaling (`DG_PARTY`, `dgParty`, `dgFightRatio`), the three entrances (`DG_ENTRANCES`: a door each on the real terrain, found by scanning it, with a signpost on the nearest road; `dgApron`, `dgEntranceNear`: the board opens only within `DG_ENT_TALK` of a door; `dgGateOpen`: Wildwood's door is shown sealed at +0; a camp keeps 32 m off a door), and the rewards in `shared/dungeon-rewards.js` (a clear pays one random level-30 item: weapons from Wildwood's dungeon, armour from the Vale's, a ring from the Reach's, rarity 70 / 25 / 4 / 0.8 / 0.2%, `DG_REWARDS`, `dgClearReward`; the level-30 gear is a tier above the six, ids `sword7-e+3`, `dgParse` / `dgItem`; the ring, 7 types, adds `ringAtk` of your weapon's attack when its element is your soul's; enhancing up to `ENH_MAX` 2 / 4 / 6 / 8 / 10 by rarity with the Tempering Stone, which normal monsters of level 30+ drop at 2.6% instead of equipment, `dgDropKind`)

`shared/dungeons.js`, `shared/dungeon-rewards.js`; the designs `docs/DUNGEON-THEMES.md`; the design, the instance plan for the server (runs are far-away slots in the same world; every global that must become per-run is listed), the missions, loot for all, the milestones: `docs/DUNGEONS.md`; test `node tools/dungeons-smoke.js` (`--show defense 7` draws one)

### Dungeon themes and bosses (**built**): the three tile kits through the theme registry (`defineDungeonTheme`, `DG_BAD`, legends, `B.props`), the three dungeon bosses (defs, kits, new primitives, client looks)

Registry, tile checks, carving, bake with props `shared/dungeons.js`; one file per theme `shared/dungeons/themes/<id>.js`; boss designs and defs `shared/dungeons/bosses.js` (`DG_BOSSES`, `DG_BOSS_DEFS`, `DG_HALL_LAMPS`, `dgVentAt`, `dgHallArena`); kits `server/dungeons/boss-kits.js`, primitives `server/dungeons/boss-fx.js`; client `game/combat/boss-dungeon.js`, `boss.js`, `boss-fx.js`, `monster-spirits.js`; design and hooks `docs/DUNGEON-THEMES.md` sections 3-4; tests `node tools/dungeons-smoke.js`, `node tools/dungeon-boss-smoke.js`

### Parties and dungeon runs, server (**built**; their client is the entry "Dungeon runs and parties, client"): the party, run slots far east of the world, events / snapshots kept per run, the walker AI, loot for all, down / revive, the mission kits' registry with Purge, the boss finale, the save `gear.dg`

Party `server/party.js` (`party{a,name}`, `/invite`, events `pty` / `ptyi`); runs `server/dungeons/`: `instances.js` (the run object, coordinates, `S.ctx` and `dgEvFor` / `dgSnapS`, setPos, hits, enter / exit), `mobs.js` (`dgSpawnS`, the AI, `rewardAllS`), `kits.js` (`dgDefineKit`, objectives, `dgBossS`), `kits/purge.js`, `runs.js` (lifecycle, down / revive, won / lost, `gear.dg`), `lobby.js` (`dg{a}` messages, `dgboard`, the testing tool `dev{cmd:'dg'}`); slots `shared/dungeon-slots.js`; hooks marked `// dungeons:` (table, protocol, the run object and primitives: `docs/DUNGEONS.md` sections 7, 7b, 9); tests `node tools/party-smoke.js`, `node tools/dungeon-runs-smoke.js`.

### Dungeon missions, server (**built**): the seven kits (Purge, Defense, Survival, Sabotage, Siege, Hunt, Escort), their shared moves, the themes' hazards, the HUD text

Kits `server/dungeons/kits/<mission>.js` (one `dgDefineKit` call each); shared moves `server/dungeons/fx.js` (kit-driven monsters `m.dgOwn` + `dgWalkS` / `dgSwingS`, channels `dgChannelS`, objectives with health, chests `dgChestS`, mouths `dgMouthsS`, packs, guardians, the run-tick hook `dgFxTickS`); hazards `server/dungeons/hazards.js` (spikes, steam, prison from the legends' `hz`); HUD text and objective kinds `shared/dungeon-hud.js` (`dgHudText`, `DG_OBJ_KINDS`); numbers and choices `docs/DUNGEONS.md` section 4 ("As built"), protocol section 9; test `node tools/dungeon-missions-smoke.js`.

Pitfalls: a monster with `m.dgOwn` is skipped by the walkers' AI after its death check, so its kit must move it every tick (guardians are moved by `dgFxTickS`); the captive is an objective, not a monster; a kit's channel has `end: Infinity` (only `updateCastsS` breaks it, `dgFxTickS` finishes it); kits count time with `dt` in `run.k` (a test may tick fast: `dgWalkS` cuts a step to 0.1 s).

### Dungeon rewards (**built**; a won run hands out the clear's piece: `dgWinS`): the 490 level-30 ids as items, the ring slot and its attack by soul, the Tempering Stone, the forge's Temper tab

Rules and ids `shared/dungeon-rewards.js`; items, `dgVisTier`, `dgMergedId`, `dgRingAtkOf`, `dgEnhInfo` `shared/dungeon-items.js`; `dgRingAtkP`, `dgRollDropP`, `dgTemperP` (`temper{id[,worn]}`), `dgGrantItemP(p,id)` (call it for each member at a clear), `MSG.rwdev` (testing tools) `server/dungeon-gear.js`; details, stone chip, the Temper tab, events `stone` / `temper` `game/economy/dungeon-gear.js`; icons `game/ui/item-icons.js` (`ringIconArt`); hooks marked `// dungeons:` (table in `docs/DUNGEON-THEMES.md` section 7); tests `node tools/rewards-smoke.js` (server), `node tools/rewards-client-smoke.js` (client, runs `dist/`: build first).

### Dungeon entrances, client (**built**): the three doors and signposts in the world, sealed or open by your gear, the talk prompt, the Delve board's hook, the ground patch, the maps

Meshes and animation `game/village/buildings-dungeon.js` (`dgEntBuild`, `dgEntUpdate`; per door a group in `DG_DOORS.doors[id]`, the signposts in `DG_DOORS.signs[id]`); rules `game/dungeon/entrances.js` (`dgEntSealed`, `dgOpenDoor(id)`: sealed -> a toast with the reason, open -> `dgBoardOpen(themeId)` if defined, else "The way is not ready yet"; `dgEntPrompt`, `dgEntTint` the ground, `dgEntClear` no plants, `dgEntMapMarks` / `dgEntMiniMarks` / `dgEntName`, `dgEntWater` / `dgEntSounds`); the data stays in `shared/dungeons.js` (`DG_ENTRANCES`, `dgGateOpen`). Hooks and choices: `docs/DUNGEON-THEMES.md` section 6. Test `node tools/entrances-client-smoke.js` (builds first: `python3 build.py`).

Pitfalls: a door's group is turned by `a`, so +z is out of the door, and props that stand on the ground take `S.gy(lx,lz)` (the ground at their own place, from the door's), never the door's height: the ground falls 1-3 m in front of two of the doors. `paint` painters take 7 arguments and `pc`'s 4 (`woodC` / `stoneC` are for `pc`: use `dgEntWood` with `paint`). A collider must be 6 m or less across. Themes are registered files (`DG_THEMES` may lack an entry), so the doors take a theme through `dgEntTheme(E)`, which falls back to what the door itself says.

### The Delve board, client (**built**): the panel a door opens, the two missions on offer, the countdown, the leader's Start, the prompt to join a party's run

`game/dungeon/board.js` (`dgBoardOpen(themeId)` sends `dg{a:'open'}`; `NETH.dgboard` fills the panel; `DG_BOARD` state; `dgBoardStart`; the join prompt `dgJoinShow(e)` for `dgi`, registered as `EVH.dgi` only if no other file did); markup `#dgBoard` / `#dgJoin` in `index.html`, `'dgBoard'` in `PANELS` (`ui/panels.js`), styles `25-dungeon-board.css`; the texts (a sentence per dungeon, a line per mission, each dungeon's names for the objectives) are tables at the top of the file. The panel shows the server's answer and checks nothing itself; it reads the roster from a global `dgPartyState` if the party code keeps one. Test `node tools/dungeon-board-client-smoke.js` (builds first: `python3 build.py`). Design: `docs/DUNGEONS.md` sections 7c, 8, 9.

Pitfalls: `dgBoardOpen` is declared inside the game's scope, so a test cannot shadow it with a `global.dgBoardOpen` (the entrances test swaps the binding with `dgBoardSwap`). Start closes the panel *before* sending, so a refusal's fresh board (which the solo server may return inside the same call) finds it closed and opens it again. The test's stub elements have `disabled: true` by default: do not test `disabled === false`.

### Dungeon runs and parties, client (**built**): the dungeon built from the `tp` at its slot, its look (fog, light, music), walls and camera, the party frame and invites, the run HUD, objectives, the results, the maps

`game/dungeon/`: `run.js` (`DG_RUN`, `dgIn()`, the tp hook `dgOnTp`, `EVH.dgo/dgb/dgr/dge`, `SNAPH.dg`, `dgFrame`), `view.js` (meshes, `DG_PROP_KINDS`, anchors, objective markers, `dgViewClear`), `look.js` (`dgLookEnv`, lights, gloom, music, ambience), `collide.js` (`dgBounds`, `dgCamBoom`), `party.js` (`dgPartyState`, frame, panel `#dgPty`, invite `#dgPtyInv`, `dgCastEv`), `hud.js` (`dgHudText` drawn, labels, arrows, the use key `dgUseNear` / `dgUseKey`, downed screen, results `#dgResult`, the Testing row), `minimap.js`; styles `24-dungeon.css`; hooks marked `// dungeons:` (table: `docs/DUNGEONS.md` section 7c); test `node tools/dungeon-client-smoke.js` (and the dungeon case of `client-smoke`), both run `dist/`: build first.

Pitfalls: a run's slot lies over the Reach or the vale by its coordinates (`inHoar`, `inVale` are true there): never ask a land function in a run, ask `dgIn()`. Pids are strings in solo (`'you'`): never `|0` one. Run monsters' health is in the def's units with `maxHp` from the roster (`m.dgK` for the level), as the server's. The point lights' count must not change inside a run (a new count recompiles every material); entering and leaving each recompile once (cached after). The headless DOM does not parse `innerHTML`: build HUD elements with `createElement` and keep references (`querySelector` returns a fresh stub each call).
